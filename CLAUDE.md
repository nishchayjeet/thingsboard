# Agent onboarding — Internal ThingsBoard PE-features fork

This is an **internal fork** of the open-source ThingsBoard CE repo with
Professional-Edition–equivalent features rebuilt on top of the Apache 2.0 source.

Read this file fully before touching code.

## What this fork is for

The upstream Professional Edition is closed-source. We are reproducing its
feature surface in this repo so we own the code under Apache 2.0. The relevant
PE feature areas are listed in **`progress.md`**, with per-feature status
(completed / partial / pending). Always read `progress.md` first.

The active session handoff lives in **`handoff.md`**. Read that next — it tells
you exactly where the last agent stopped.

## Working conventions

### Commits
- Commit frequently in logically-grouped chunks. Don't batch a whole session
  into one mega-commit.
- Commit messages: imperative mood, plain prose ("add scheduler poller",
  "fix RBAC fallback when role grants are empty"). One-line subject + optional
  body explaining the *why*.
- **Do not attribute commits to AI assistants.** No "Co-Authored-By: Claude",
  no "Generated by …" trailers, no emoji robot signatures. The git author is
  the human running the agent.
- Don't commit `.env`, `build-artifacts/`, or anything containing real
  credentials.

### Tests
- Run `mvn -pl <module> test` for the module you touched before declaring work
  done. For changes that span modules (e.g. new entity + DAO + controller), run
  `mvn -pl common/data,common/dao-api,dao,application -am test`.
- Add tests alongside new functionality. Service classes in `dao/` have JPA-
  test patterns under `dao/src/test`; controllers in `application/` have
  WebMvc tests under `application/src/test`.
- If you cannot add a test, say so explicitly in the handoff — don't silently
  skip.

### Security review
- Before committing any new controller or any change to authorization code,
  invoke the `/security-review` slash skill on the diff. Triage findings
  inline; document residual risk in `handoff.md`.
- Particular sharp edges in this codebase:
  - Public endpoints under `/api/noauth/**` and `/api/v1/**` bypass JWT auth.
    Anything new there needs an alternative auth gate (routing key + shared
    secret, signed payload, etc.).
  - `JdbcTemplate` SQL must always use `?` parameter binding. Never
    concatenate user input into the SQL string.
  - The headless-Chrome-based report generator forks a process; the dashboard
    URL it visits comes from a server-stored `ReportConfig` (not user input),
    but any future change that lets users control the URL needs SSRF review.
  - GraalVM/JS execution is **deliberately not wired** in `ScriptConverter` —
    don't add it back without the script-isolation review.

### How to build & test
- **Local build**: `mvn clean install -DskipTests -Dlicense.skip=true`
- **Local dev (app on Mac, Postgres on remote)**: `./deploy/dev-run.sh` after
  copying `deploy/.env.example` to `.env` and filling it in.
- **Full server deploy (build on Mac, ship to remote)**: `./pefeatures-build.sh`.
  See script header for env vars. **Never put credentials in this file or any
  committed file** — they live only in `.env` (gitignored) or your shell.

### Configuration
- Server creds, image tags, deploy paths: env vars only. See
  `deploy/.env.example` for the full list.
- Never refer to credentials inside committed files, scripts, README content,
  or commit messages. If something needs documenting, document the variable
  name, not the value.

## Feature scope reference

We're tracking the PE feature surface against
<https://thingsboard.io/docs/pe/>. The PE-vs-CE comparison the maintainers
publish is the source of truth for what counts as "PE parity":

| Area              | What PE provides                                     |
|-------------------|------------------------------------------------------|
| White-labeling    | logo/favicon, palette, login page, custom email      |
| Advanced RBAC     | custom roles, per-entity grants, entity groups       |
| Integrations      | AWS IoT, Azure, IBM Watson, Kafka, ChirpStack, TTN,  |
|                   | Loriot, OPC-UA, generic MQTT/HTTP/UDP/TCP            |
| Codec library     | 400+ pre-built device payload decoders               |
| Scheduler         | cron/recurring UI-driven event trigger               |
| Reports           | scheduled PDF dashboard snapshots → email            |
| Solution templates| pre-packaged dashboards+rules+profiles deployable    |

Before implementing or modifying a feature, **check the corresponding
`thingsboard.io/docs/pe/user-guide/<feature>/` page** so the API surface
matches. PE's REST routes and entity field names should be our reference.
Diverging is fine when justified; document the divergence in `progress.md`.

## Repo layout for PE additions

```
common/data/src/main/java/org/thingsboard/server/common/data/
  wl/         white-labeling params
  scheduler/  ScheduledEvent + ScheduleConfig
  role/       Role
  integration/Integration, Converter, IntegrationType
  codec/      PayloadCodec
  solution/   SolutionTemplate
  report/     ReportConfig
  id/         {Role,ScheduledEvent,Integration,Converter,PayloadCodec,SolutionTemplate,ReportConfig}Id

common/dao-api/.../<area>/<Area>Service.java          ← interfaces
dao/.../<area>/<Area>ServiceImpl.java                 ← JdbcTemplate impls
application/.../controller/<Area>Controller.java      ← REST endpoints
application/.../service/<area>/...                    ← runtime (poller, manager, runner)
```

DB tables for these entities are in:
- `dao/src/main/resources/sql/schema-entities.sql` (fresh installs)
- `application/src/main/data/upgrade/lts/schema_update.sql` (existing installs)

When adding a new entity type, mirror this layout and update
`common/data/.../EntityType.java`.

## Handoff workflow

At the end of every agentic session, **update `handoff.md`** with:
- **Goal** — what you/the user were trying to accomplish this session.
- **Current state** — concrete: which features compile, which were touched,
  which tests pass.
- **Changed** — files modified, grouped by feature.
- **Failed attempts** — what didn't work and the reason, so the next agent
  doesn't redo it.
- **Next steps** — ordered list, most-blocking first.

Also update `progress.md` if any feature's status changed.

## Don'ts

- Don't reformat / re-indent unrelated code.
- Don't bump CE dependency versions unless the user asked.
- Don't rename existing CE classes; add new ones alongside.
- Don't commit `.env`, build artifacts, IDE files, or large binaries.
- Don't put credentials anywhere in the repo or any commit message.
- Don't add AI-assistant attribution to commits.
